# PoC 證據格式 v1.0｜共用提交與失敗代碼

## 1. 每份測試證據最低欄位

`testId`, `backend(firebase|postgres)`, `fixtureHash`, `gitCommit`, `expectedCanonical`, `actualCanonical`, `status`, `startedAt`, `finishedAt`, `traceId`, `evidenceFiles`。格式參見 `contracts/evidence-schema-v1.0.json`。

`status` 允許 `NOT_RUN`, `PASS`, `FAIL`, `BLOCKED`, `SKIPPED`。缺少證據時不得宣稱 PASS；無法執行時標 BLOCKED，並寫明原因。

## 2. 提交錯誤語意

| 程式結果 | 適用情況 | 必要行為 |
|---|---|---|
| `FORBIDDEN` | 角色／工作空間／資料範圍不符 | 不回傳可識別敏感資料 |
| `VERSION_CONFLICT` | expectedVersion 過舊 | 不寫正式紀錄，提示人工處理 |
| `OPERATION_REUSE_MISMATCH` | operationId 被不同 payload／actor／target 重用 | 拒絕且不外洩原請求收據 |
| `LOCAL_SAVE_FAILED` | IndexedDB／儲存空間不足等寫入失敗 | 不顯示「本機已可靠保存」 |
| `DERIVED_PENDING` | 正式來源已提交但衍生更新未完成 | 來源正式成功，衍生視圖不可冒稱最新 |
| `UNAVAILABLE` | 無法確認伺服器提交／網路失聯 | 允許以原 operationId 恢復查詢，不自行產生新操作 |

以上為技術中立的**預期語意**，不是既有 API 的真實回應。

## 3. 收集方法

- 各測試先重設為原始 fixture／版本，記錄 fixtureHash；每項結果需包含對應的原始資料或脫敏雜湊證據。
- 正式 current、Revision、OperationReceipt、AuditEvent 四者的原子性必須一起證明；同個 operationId 重試不可產生第二次版本變更。
- 匯出／截圖不能含實際學生電話、醫療或家庭細節；僅用全虛構資料。
- `evidence/runs/` 在 `.gitignore` 中；整理公開證據包之前，必須過濾金鑰、令牌、裝置辨識及個資。
- 無論在 Firebase 還是 PostgreSQL，若 P0 未 PASS，不進入正式架構選型。
