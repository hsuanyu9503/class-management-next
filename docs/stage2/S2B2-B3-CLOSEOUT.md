## 2. 剩餘項目的分類

### 2.1 阻擋網站功能開發

**限定範圍的結論**（v0.2）：技術殘餘項目**不阻擋**下列工作——獨立的畫面原型、使用虛構或假資料的 UI，以及不依賴未決能力的功能。
這**不**保證真實資料、完整授權或正式後端可以立即使用：
- 真實資料要等後端的技術選型（§2.2）；
- 授權要依各功能用到的 capability 個別檢查（下表）。

前提如下：

| 項目 | 依據 | 最小完成條件 |
|---|---|---|
| 網站的範圍與規格 | `SPEC.md` §1（不是正式網站）；`DESIGN.md` 是範本 | 負責人決定：在哪個 repository、做哪些功能；更新或新增 SPEC 與 DESIGN 的頁面規格，經審查 |
| 涉及授權的功能，對應的 D-01～D-16 | `S2B1-AUTHORIZATION.md` §12（決定前預設拒絕） | **逐功能檢查**：只有用到該 capability 的功能才受影響，未決的能力維持拒絕或停用。例如科任點名 D-05、匯出 D-08、敏感請假資訊 D-06 在核准前維持拒絕。不把所有 D-xx 都當成每個畫面的前置條件 |

### 2.2 只阻擋正式 PASS／技術選型（不是網站上線）

三件事要分清楚（v0.2）：
1. **PoC 證據的簽章 PASS**（`PASS_ENABLED`）：只代表某一個案例的 statement 可以被簽章；
2. **技術選型的放行**（Stage 5 ADR）：需要 P0=20/20 PASS 等條件；
3. **未來網站的正式上線**：發布規格**尚未定義**，這份收尾文件**不能**完成它的放行。

開啟 PASS **不等於**全部 PoC 通過，也**不等於**網站可以發布。Stage 3～5、真機與 ADR 的門檻留在技術選型這條線上：它們不阻擋獨立的 UI 原型，但也不能因為做了原型就跳過正式的選型決策。

## 3. 下一批的提案（**需要負責人決定方向**）

在目前的規格下，Claude 不自行選擇新需求。以下兩個方向列出來供負責人決定，各附使用者看得到的成果與驗收方式。

### 方向 A：在本 PoC 範圍內，擴充 Stage 2 的案例覆蓋（符合現行 SPEC）

- **內容**：在 Firebase emulator 中，把 36 個案例中**還沒接上**的 P0 案例，分批接上同一套 Runner／Observer／Verifier。第一批建議 4～6 個 P0，從 DOMAIN 或 TX 分組挑選，不需要 G-1～G-4 決策的案例。
- **使用者看得到的成果**：每個案例一份本機與 hosted 的結果（最多 `UNATTESTED`），以及更新後的案例對照表：哪些已接上、哪些 BLOCKED、原因是什麼。
- **驗收方式**：
  - 單元測試與 emulator 整合測試；
  - hosted `attest.yml` run 的結果為 `UNATTESTED`；
  - 案例對照表與 Stage 1 的契約一致；
  - 不放寬任何 P0（放行門檻）。
- **不新增** workflow 檔，也不另造簽章基礎設施；但**需要修改既有的 workflow 與工具鏈**（v0.2）：
  - `.github/workflows/attest.yml` 的 dispatch 選項目前只有 POC-001／002／008／009，push 固定是 POC-001；
  - `poc/stage2/scripts/run-attest-execute.mjs` 也只接受這四個 ID，其他 ID 會以 2 退出；
  - 若新案例要有 hosted 證據，該批的計畫必須列出輸入白名單、執行器與相關測試的必要擴充。這些是受保護的變更，需要重新審查並核准錨定；
  - 不承諾「只要接上 Adapter 就能跑所有新案例」。
- 具體的 4～6 個 P0 案例 ID **尚未列定**。要在該批的計畫中逐一確認：不依賴未決的能力（D-xx），也不依賴 G-1～G-4。

### 方向 B：開始網站功能開發（需要先變更範圍）

- **先讀既有規格**（v0.2）：`SPEC.md` 提到 `Homework-manager-` 與 M02-04／M02-05 已定案的功能與視覺規格。若選 B，Claude 先讀取這些既有的產品規格與設計，沿用已定案的內容，不要求重新定義；只有在無法取得時，才列出真正缺少的資訊。
  - 那些規格不在本 repository 中。目前本 session 只能存取 `class-management-next`，需要負責人提供，或同意加入該 repository（唯讀）。
  - 在讀到原規格之前，`DESIGN.md` 的範本色票與下面的候選名冊頁，都**不是**正式決策。
- **前置**（負責人決定）：
  - 在本 repository 還是另一個 repository 開發（`SPEC.md` 目前排除了本 repository）；
  - 第一個頁面或功能；
  - 後端：技術選型尚未完成（Stage 5），第一批可以先用 mock 或本機資料；
  - 填好 DESIGN 的頁面規格與設計 tokens。
- **候選的第一批**（只是舉例，以負責人的規格為準）：唯讀的「班級點名名冊」頁面，使用 Stage 1 的虛構固定測資。
  - 使用者看得到的成果：手機、平板、桌面三種版面的名冊頁；
  - 驗收方式：DESIGN §7 的視覺驗收清單、鍵盤操作、`prefers-reduced-motion`、三種寬度沒有水平溢出、不使用真實學生資料。
- 正式資料與授權相關的功能，要等相關的 D-xx 決策（§2.1）。

### Claude 的建議

- 兩個方向並列，由負責人決定。Claude 不因為舊 SPEC 的 PoC 定位，就預設負責人仍要繼續 A（v0.2）。
- 若要開始做網站（B），最小的範圍決策只有四項：
  1. 在哪個 repository 開發；
  2. 提供或同意讀取既有的網站規格與設計（`Homework-manager-`、M02-04／M02-05）；
  3. 第一個使用者流程，例如唯讀的名冊頁；
  4. 第一批只用虛構資料，不接正式後端。
  - 不需要先完成 Stage 2～5，也不需要先處理無關的 PoC 追蹤項目。真實授權與後端連線，之後依選定的能力另行處理。
- 若目標仍是技術選型（A），它符合現行規格，也直接推進 Stage 2 → Stage 5 的門檻；但需要上面列出的 workflow 與執行器的擴充。
